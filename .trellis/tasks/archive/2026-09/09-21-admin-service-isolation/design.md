# 独立后台服务与订单商品管理：技术设计

## 1. 目标与边界

ChongHub 需要一个可独立发布和回滚的运营后台，承载订单查看/人工履约及商品、SKU 管理，同时不因后台 Web 进程的发布或故障直接中断公开站点。业务数据库仍是单一 PostgreSQL，避免订单与商品跨库同步。

本设计只覆盖服务边界、认证/API、商品可售状态、订单一致性、部署回退和验证。在线支付、自动履约、多员工角色、独立报表和独立业务数据库不纳入本次实现。

## 2. 架构与服务边界

仓库保持 monorepo，但产出两个可单独启动的 Next 服务：

- `web`：公开页面、公开商品 API、下单、用户查单和公开售后入口。
- `admin`：管理员登录、后台页面、后台订单/商品/设置 API 和人工履约操作。

两服务共享类型化领域模块、数据库访问模块和 PostgreSQL。共享代码不代表共享运行时：每个服务拥有独立进程、端口、健康检查、日志和镜像。后台不通过 HTTP 调公开站点，公开站点也不依赖后台服务；双方直接读取同一数据库中已提交的业务状态。

本地默认公开服务 `3000`、后台服务 `3001`，生产由反向代理映射到公开域名和 `admin` 子域名。后台进程停止或回滚不影响公开进程；数据库不可用仍会影响依赖数据库的两边，这是明确的基础设施边界。

服务拆分不能只增加一个端口：实施时必须提供两个服务入口、独立构建产物/启动命令、各自的路由白名单和健康检查。公开构建不得打包或暴露后台页面与后台 API；后台构建不得改变公开服务的启动契约。共享领域模块通过显式 import 边界复用，不能用运行时跨服务调用来伪装隔离。

## 3. 认证与 API 契约

现有单管理员身份表继续作为授权来源，普通用户登录不能获得后台权限。后台使用独立的会话 Cookie 名称和专用登录入口，属性为 `HttpOnly`、生产 `Secure`、`SameSite=Lax`、限定后台域名；公开服务不接受该 Cookie。

公开 API 继续只返回公开 DTO。后台 API 只挂载在 admin 服务并返回管理 DTO，至少包括：订单列表/详情、人工命令、商品/SKU 编辑、上架、下架、售罄、恢复售卖、通知重试和设置。所有写操作继续使用服务端鉴权、CSRF 校验、事务、幂等键和审计事件；不把公开单号当作认证凭据。

## 4. 商品状态与数据流

保留 `products.status` 和 `skus.status` 的 `draft/published/unlisted` 生命周期语义；新增 SKU 级 `availability`（`available` / `sold_out`）。公开目录查询条件为商品和 SKU 均 `published`，但返回售罄标志；售罄套餐显示但禁用下单。

下单事务锁定 SKU 并同时校验 `status='published' AND availability='available'`，失败时返回明确的不可购买错误且不创建订单。后台修改商品状态、SKU 状态或可售状态时，在同一事务中写入审计记录。历史订单使用已有快照，不被后续价格或状态变更重写。人工售罄不是库存扣减：与后台状态变更并发的下单以各自事务提交顺序为准，售罄提交后开始的新订单必须拒绝。

## 5. 兼容迁移与发布顺序

按 expand/contract 顺序执行：

1. 先增加 `skus.availability` 及索引/约束，默认 `available`；旧公开服务仍可运行。
2. 发布兼容读逻辑和后台读页面；确认旧数据全部具备安全默认值。
3. 发布后台写 API 和下单强校验；再启用售罄管理 UI。
4. 最后切换管理员使用独立后台域名，保留现有公开路径兼容窗口。

数据库迁移由一次性 migration job 执行，两服务只读取已完成版本。回退优先回滚应用镜像或停止后台写入，不执行破坏性 down migration；必要时使用前向修复纠正状态。

## 6. 测试与运维

- 单元：状态转换、非法组合、售罄/恢复、订单创建可售校验。
- 集成：后台修改对公开查询可见；售罄提交后新订单被拒绝且并发事务按提交顺序得到确定结果；历史订单快照不变；权限、幂等和审计正确。
- 服务隔离：后台停止时公开浏览和下单继续可用；公开服务停止时后台 API 在数据库正常时继续可用。
- 构建/运行：分别构建两个服务，分别启动并检查健康端点、静态资源、管理员登录、商品修改和订单查询。
- 运维：补充双服务启动/停止、迁移顺序、日志、健康检查、备份恢复演练和回滚步骤。

## 7. 风险与取舍

- 共享数据库仍是共同故障域；通过连接池、健康检查、事务和备份演练降低风险，不声称完全隔离。
- 两服务共享领域模块，数据库迁移必须向后兼容；通过 expand/contract 和发布顺序控制版本耦合。
- 独立后台域名需要反向代理和 Cookie 配置；本地用两个端口模拟同样边界，避免开发环境掩盖生产问题。
