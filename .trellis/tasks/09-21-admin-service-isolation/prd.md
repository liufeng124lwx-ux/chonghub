# 独立后台服务与订单商品管理

## 目标

为 ChongHub 提供一个与公开交易站点隔离的运营后台，用于查看和处理订单、管理商品可见性与售罄状态，降低后台代码变更对线上公开服务可用性的影响，并让日常运营入口更清晰。

## 已确认的仓库事实

- 当前项目是单体 Next.js 应用，公开页面、`/admin` 页面和 `/api/admin/*` 路由共用一个进程与同一 PostgreSQL 数据库。
- 当前已存在管理员订单工作台、商品价格编辑、商品发布和设置页面；管理员通过普通登录会话进入 `/admin`。
- 商品表已有 `draft`、`published`、`unlisted` 三种状态，SKU 也有相同状态；公开商品查询只返回商品与 SKU 都为 `published` 的记录。
- 订单创建会保存商品快照，因此修改商品价格不会改写历史订单金额。
- 现有项目明确没有在线支付和自动履约，首版是人工收款、人工交付；生产操作文档要求数据库迁移采用前向修复并可回退应用镜像。

## 当前需求

- 后台可查看订单及其运营处理状态。
- 后台可管理商品，至少支持上架、下架、售罄/恢复售卖，以及现有的价格编辑能力。
- 后台服务与公开服务在部署/进程层面隔离，使后台发布或故障不直接拖垮公开站点。
- 订单和商品数据仍需保持一致，公开站点能及时反映后台已确认的商品状态。
- 管理员身份沿用单管理员模型，但后台使用独立域名/专用会话，不与公开站点共享管理员 Cookie。

## 初步范围

### In scope

- 后台订单列表/详情与现有订单处理动作的独立承载。
- 商品和 SKU 的编辑、上架、下架、售罄及恢复售卖。
- 公开目录与后台修改之间的明确数据契约、并发/失败处理和部署回退策略。

### Out of scope（当前暂不纳入）

- 在线支付、自动充值或自动履约。
- 多角色员工权限、复杂审批流和独立报表系统。
- 将订单主库拆成另一套数据库并自行解决跨库一致性（除非后续明确选择该方案）。

## 验收标准

- 后台服务可单独启动、停止和发布，公开站点仍可独立提供公开商品浏览与下单。
- 管理员执行商品上下架/售罄后，公开站点按照定义的语义阻止或允许新订单，历史订单不受影响。
- 售罄状态提交前已进入事务的订单按数据库提交结果处理；售罄状态提交后开始的新订单全部被拒绝，不引入未定义的库存扣减语义。
- 后台查看订单、执行现有人工履约动作的结果与公开订单状态一致。
- 后台服务不可用时，公开站点的既有公开读/下单路径不因后台 UI 进程崩溃而中断；数据库或共享业务服务不可用时按现有错误策略明确失败。
- 关键修改可审计、可验证并有应用级回退路径。

## 已确认的关键决策

- 后台采用独立进程/容器与独立域名，共享 PostgreSQL；不拆独立业务数据库。
- 售罄是 SKU/套餐级状态。售罄套餐继续展示但不可新下单，其他套餐不受影响；恢复售卖后继续可下单。
- 下架与售罄分离：生命周期状态继续使用 `draft/published/unlisted`，另加可售状态 `available/sold_out`。
- 首版保持单管理员身份；后台使用专用会话 Cookie，不与公开站点共享管理员 Cookie。
- 新增字段与服务拆分采用向后兼容迁移；应用回退优先，不执行破坏性 down migration。

## 交付边界

本任务包含服务拆分、后台认证/API 边界、SKU 售罄与下单校验、现有订单后台迁移、测试和运维文档。在线支付、自动履约、多角色权限、跨库同步和报表系统不在范围内。
